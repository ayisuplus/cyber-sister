## 一、总体原则

1. **审查是教学，不是审判** — 每条评论至少让作者学到一件事
2. **一次审完，别挤牙膏** — 一次性给出完整反馈，避免来回拉扯
3. **对事不对人** — 讨论的是代码，不是写代码的人
4. **优先级分明** — 🔴 必须改 / 🟡 建议改 / 💭 小瑕疵，不要把所有问题都当 blocker
5. **看到好代码要夸** — 好的模式值得被看见、被学习

## 二、五大审查维度

### 2.1 正确性（Correctness）

代码是否做了它该做的事？

| 检查项 | 说明 |
|--------|------|
| 边界条件 | 空数组、null、undefined、超长字符串、并发请求 |
| 异步流程 | async/await 是否配对、Promise 是否有 catch、竞态条件 |
| 状态一致性 | 前端 store 与后端数据库是否可能不同步 |
| 错误处理 | 关键路径是否有 try-catch、错误是否被静默吞掉 |
| 类型安全 | 类型转换是否显式、`==` vs `===`（JS）|

**本项目要点：**
- 聊天持久化必须全有或全无（用户消息与 AI 消息同事务），不允许出现只存一半的状态
- 危机检测必须先于任何模型调用执行，命中即阻断，模型调用次数为零
- 注释与代码必须一致；逻辑变更时同步更新注释

### 2.2 安全性（Security）

是否存在可被利用的漏洞？

| 检查项 | 说明 |
|--------|------|
| 注入风险 | SQL 注入、命令注入、XSS、Prompt 注入 |
| 认证授权 | Token 验证是否完整、是否有越权访问 |
| 敏感信息 | 密钥/密码是否硬编码、日志是否泄露敏感数据 |
| 输入校验 | 用户输入是否经过验证和清洗 |
| CORS/CSP | 跨域策略是否最小化 |

**本项目红线（不可协商）：**
- 密钥与口令只经仓库外只读 secret 文件注入，严禁硬编码或入库
- `jwt.verify` 必须显式指定 `algorithms`，防止算法混淆攻击
- 日志必须脱敏：手机号、聊天内容、记忆内容不进入日志（见 `docs/06-合规/内容审核策略.md` 与 Spec §8）
- llama.cpp 地址只接受 `LOCAL_LLM_ALLOWED_ORIGINS` 中的精确匹配，Qwen 云端链路必须经用户显式同意门控

### 2.3 可维护性（Maintainability）

6 个月后接手的人能看懂吗？

| 检查项 | 说明 |
|--------|------|
| 命名 | 变量/函数名是否自解释、是否一致 |
| 函数长度 | 单函数超过 50 行考虑拆分 |
| 注释质量 | 解释"为什么"而非"做了什么" |
| 模块耦合 | 模块间是否通过明确接口通信 |
| 配置管理 | 魔法数字是否提取为常量/配置 |

**本项目要点：**
- 危机识别、人格提示词等关键词/文案集中在 `packages/llm-gateway` 的人格与检测配置中维护，业务代码不重复硬编码
- 危机资源文案属于须经产品负责人书面批准的内容，代码中不得私自改写（见 `docs/06-合规/合规审查清单.md`）
- 跨包契约（如 `apps/api` 与 `packages/llm-gateway` 之间）变更时必须同步迁移全部调用点，不留兼容 shim

### 2.4 性能（Performance）

有没有明显的瓶颈？

| 检查项 | 说明 |
|--------|------|
| N+1 查询 | 循环中是否有数据库/API 调用 |
| 内存泄漏 | 事件监听是否清理、大对象是否及时释放 |
| 不必要的计算 | 是否有重复计算可以缓存 |
| 外部调用 | LLM 调用是否有超时、降级与取消机制 |
| 前端渲染 | 是否有不必要的重渲染、列表是否用 key |

**本项目要点：**
- 本期产品是模块化单体 + 单机 llama.cpp，审查重点是明显的浪费（N+1、重复渲染、无超时调用），而非规模化架构
- 妆教模块的图片/视频帧分析必须停留在浏览器本地，任何把媒体数据外发的"优化"都是红线

### 2.5 测试（Testing）

关键路径有测试覆盖吗？

| 检查项 | 说明 |
|--------|------|
| 核心逻辑 | 危机识别、人格切换、记忆、工具箱、妆教分析是否有单元测试 |
| API 测试 | 主要接口是否有集成测试 |
| 边界测试 | 异常输入、超时、服务不可用是否覆盖 |
| 测试可运行 | 测试是否能独立运行、不依赖外部服务、不依赖真实墙钟日期 |
| 回归保护 | 修 bug 时是否同步补充测试 |

**本项目基线（准则性表述，以各包配置为准）：**
- `apps/api`、`apps/web`、`packages/makeup-skill` 的 `vitest.config.*` 已配置 **80% 覆盖率阈值**（lines/statements/functions），`pnpm test:coverage` 不得低于该阈值
- 各包 lint 规则以各自的 `eslint.config.js` 为准，提交前必须通过
- `apps/web` 的关键用户路径由 `e2e/`（playwright）守护
- `packages/llm-gateway` 暂无直接测试（已登记为 `docs/README.md` 已知问题 #8），新增代码应随流式工作包补齐同级标准

## 三、分模块审查重点

### 3.1 `apps/api`（Express + Prisma 后端）

```
重点关注：
├── 路由层
│   ├── 非公开接口是否有鉴权中间件保护
│   ├── 请求参数是否经过校验
│   └── 响应格式与错误码是否统一（见 docs/04-开发/API文档.md）
├── 服务层
│   ├── 数据库多表写入是否用事务（聊天持久化必须全有或全无）
│   ├── 外部调用（LLM 网关等）是否有超时与降级
│   └── 错误是否向上抛出而非静默处理
├── 中间件
│   ├── JWT 验证是否指定 algorithms
│   ├── 限流策略是否合理（登录类接口更严格）
│   └── 日志是否脱敏（手机号/聊天内容不落日志）
└── 数据层（Prisma）
    ├── 查询是否只取需要的字段（select）
    ├── 关联查询是否有 N+1 问题
    ├── 用户只能访问自己的数据（where 条件含 userId）
    └── 迁移只用 prisma migrate deploy，禁止 db push
```

### 3.2 `apps/web`（React 18 + Vite 前端）

```
重点关注：
├── 组件
│   ├── 是否有不必要的重渲染（useMemo/useCallback）
│   ├── 事件监听是否在 useEffect 中清理
│   ├── 条件渲染是否处理了 loading/error/empty 三态
│   └── 列表渲染是否有稳定 key
├── 状态管理（Zustand）
│   ├── persist 的数据是否包含敏感信息
│   ├── 异步操作是否有竞态保护
│   └── 状态更新是否最小化（不要整个对象替换）
├── 网络请求
│   ├── 是否有统一的错误处理
│   ├── token 刷新逻辑是否处理并发
│   └── 请求取消（组件卸载时）
├── 样式
│   ├── 是否使用 packages/design-tokens 的 --cs-* 令牌（不硬编码颜色）
│   ├── 响应式断点是否统一
│   └── 是否满足无障碍清单（PR 模板必查）
└── 测试
    ├── 组件与 store 的 vitest 用例是否同步更新
    └── 关键用户路径是否落在 e2e/（playwright）覆盖内
```

### 3.3 `packages/makeup-skill`（React 19 + Express 5 妆教模块）

```
重点关注：
├── 隐私红线
│   ├── 图片/视频帧分析是否全部在浏览器本地完成
│   ├── 解释 API 是否只接受规范化特征标签 + lookId（不收原始媒体）
│   └── MediaPipe/WASM 资产是否按 SHA-256 校验（缺失则构建失败）
├── 前端
│   ├── 触控目标、键盘导航、reduced-motion 等无障碍约定是否保持
│   └── 与主应用共享的设计令牌是否来自 design-tokens
└── 后端
    ├── 输入是否有严格 schema 验证（防 mass assignment）
    ├── CSRF / CSP / 安全头配置是否保持
    └── 埋点是否不含可识别个人信息
```

### 3.4 `packages/llm-gateway`（模型网关）

```
重点关注：
├── 路由策略
│   ├── 本地优先（llamacpp）路由是否默认生效
│   ├── qwen 云端降级是否仅在用户显式授权后启用
│   └── 未配置本地模型时是否返回诚实的降级错误码
├── 人格提示词
│   ├── 人格定义是否集中在人格配置文件中维护
│   └── 提示词层不替代服务端安全层（危机识别永远在服务端 detection 层）
└── 契约
    └── 与 apps/api 的接口契约变更是否同步迁移全部调用方
```

### 3.5 `packages/design-tokens`（共享设计令牌）

```
重点关注：
├── --cs-* 变量是否为唯一令牌源（apps/web 与 makeup-skill 都从它消费）
├── 令牌变更是否与 docs/UI设计系统规范_V3.0.md 一致
└── 是否引入运行时依赖（该包应保持零依赖纯 CSS）
```

## 四、审查流程

### 4.1 流程总览

```
开发者提交 PR
    │
    ▼
本地自动化检查（仓库当前无 CI，见 docs/README.md 已知问题 #7）
├── pnpm lint（各包 eslint.config.js）
├── pnpm typecheck
├── pnpm test（含 vitest 80% 覆盖率阈值）
└── pnpm build（含 MediaPipe/WASM 资产校验）
    │
    ▼ 通过
分配审查者
├── 1人必审（核心链路2人）
├── 48小时内完成审查
└── 审查者不能是代码作者
    │
    ▼
代码审查
├── 第一轮：完整审查（所有维度）
├── 作者修复 → 回复每条评论
├── 第二轮：确认修复 + 回归检查
└── 特殊情况：面对面/语音讨论
    │
    ▼
合并
├── 所有 🔴 问题已解决
├── 🟡 问题有明确跟进计划
├── .github/PULL_REQUEST_TEMPLATE.md 合规与安全必查清单全部打勾
└── 本地检查全绿
```

### 4.2 PR 提交规范

以仓库根 `.github/PULL_REQUEST_TEMPLATE.md` 为准，其中的**合规与安全必查清单**（AI 身份可见、日志脱敏、危机文案已书面批准、未弱化红线、未情感诱导付费）与**无障碍清单**是合并门禁，逐项打勾，不可跳过。

### 4.3 审查者分配规则

| 模块 | 主要审查者 | 备选审查者 | 说明 |
|------|-----------|-----------|------|
| `apps/api` 路由/服务 | 后端工程师 | 全栈 | API 变更需检查前后端一致性 |
| `apps/api` 危机/合规相关 | 后端工程师 + 产品负责人 | - | 涉及红线文案与检测逻辑，必须双人 |
| `apps/web` | 前端工程师 | 全栈 | UI 变更需附截图 |
| `packages/makeup-skill` | 前端工程师 | 全栈 | 隐私红线（本地分析）必须复核 |
| `packages/llm-gateway` | 后端工程师 | - | 关注路由策略与人格配置 |
| `packages/design-tokens` | 前端工程师 | - | 需两个消费包同时验证 |
| 配置/文档 | 任意工程师 | - | 低风险，快速通过 |

### 4.4 审查时间承诺

| PR 规模 | 审查时限 | 说明 |
|---------|---------|------|
| < 50 行 | 24 小时 | 小修复，快速响应 |
| 50-200 行 | 48 小时 | 常规功能开发 |
| 200-500 行 | 72 小时 | 大功能，建议拆分 |
| > 500 行 | 拒绝审查 | 要求拆分后重新提交 |

## 五、审查评论规范

### 5.1 优先级标记

| 标记 | 含义 | 合并条件 |
|------|------|---------|
| 🔴 | Blocker - 必须修复 | 不修不能合并 |
| 🟡 | Suggestion - 建议修复 | 可本次或下次迭代修 |
| 💭 | Nit - 小瑕疵 | 不阻塞合并 |
| 👍 | Praise - 写得好 | 纯表扬 |
| ❓ | Question - 有疑问 | 需要作者解释 |

### 5.2 评论格式模板

````markdown
🔴 **安全: JWT 算法混淆攻击**（示例）
文件: `apps/api/src/middleware/auth.js`

**问题:** `jwt.verify(token, JWT_SECRET)` 未指定 algorithms 参数。

**为什么:** 攻击者可构造 header 为 `{"alg": "none"}` 的 token 绕过验证，
或使用 RS256 公钥作为 HS256 密钥伪造签名。

**建议:**
```js
const decoded = jwt.verify(token, JWT_SECRET, { algorithms: ['HS256'] })
```

**参考:** https://auth0.com/blog/critical-vulnerabilities-in-json-web-token-libraries/
````

### 5.3 禁止的评论方式

❌ "这代码写得不好"（不具体）
❌ "你怎么又犯这个错误"（对人不对事）
❌ "改了"（无解释）
❌ 只说问题不给方案
❌ 在公开 PR 中讨论绩效/能力

## 六、自动化检查配置（仓库现状）

各包自治，以包内配置文件为准，审查时直接引用：

| 包 | Lint | 测试 | 覆盖率阈值 |
|----|------|------|-----------|
| `apps/api` | `eslint.config.js`（flat config） | `vitest run` | `vitest.config.js`：lines/statements/functions ≥ 80% |
| `apps/web` | `eslint.config.js`（含 react 规则） | `vitest run` + `e2e/`（playwright） | `vitest.config.js`：lines/statements/functions ≥ 80% |
| `packages/makeup-skill` | `eslint.config.js` | `vitest run` | `vitest.config.ts`：lines/statements/functions ≥ 80% |
| `packages/llm-gateway` | 根级 eslint 覆盖 | 暂无直接测试（已知问题 #8，随流式工作包补齐） | 补齐时对齐 80% |
| `packages/design-tokens` | 根级 eslint 覆盖 | 构建即验证 | 不适用（纯 CSS） |

通用约定：

- 格式化交给 Prettier，审查不讨论格式问题
- 禁止 `console.log` 调试残留、`debugger`、`==`（以各包 eslint 规则为准）
- 根级 `pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm build` 是提交前自检命令
- 依赖变更需说明理由；`pnpm-lock.yaml` 只维护根级一份

## 七、问题登记与跟进

**本文档不维护具体代码问题清单**（file:line 级清单会随代码演进而腐烂，曾因此产生误导）。发现问题的正确路径：

1. PR 内能解决的，直接在审查评论中解决
2. 超出手头 PR 的，用 `.github/ISSUE_TEMPLATE/docs-update.yml` 或 `bug-report.yml` 提 issue
3. 文档与实现的冲突，登记进 `docs/01-产品/开发计划与路线图.md` §1.3 与 `docs/README.md` 的「已知文档问题」表，由产品负责人裁定（流程见根 `AGENTS.md` 文档规范节）

## 八、审查文化建设

### 8.1 审查者守则

1. **先理解意图，再看实现** — 读 PR 描述，不清楚就问
2. **区分偏好和标准** — "我更喜欢这样写"不是审查意见
3. **给出具体建议** — 不要只说"这里不好"，要说"建议改成 X 因为 Y"
4. **及时响应** — 不要让 PR 等超过承诺时间
5. **承认不确定性** — "我不确定，但..."比假装全知好

### 8.2 作者守则

1. **PR 要小** — 一个 PR 解决一个问题，200 行以内最佳
2. **自己先审一遍** — 提交前自己 diff 一遍，消灭低级错误
3. **回复每条评论** — 即使不同意，也说明原因
4. **不要玻璃心** — 审查的是代码，不是你
5. **学到东西要记录** — 好的审查意见沉淀为团队规范

### 8.3 定期回顾

- **每两周**：统计审查数据（PR 数量、平均审查时长、blocker 比例）
- **每月**：回顾高频问题，更新检查清单
- **每季度**：审查标准大版本更新，纳入新发现的模式
