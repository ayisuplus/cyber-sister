## 一、总体原则

1. **审查是教学，不是审判** — 每条评论至少让作者学到一件事
2. **一次审完，别挤牙膏** — 一次性给出完整反馈，避免来回拉扯
3. **对事不对人** — 讨论的是代码，不是写代码的人
4. **优先级分明** — 🔴 必须改 / 🟡 建议改 / 💭 小瑕疵，不要把所有问题都当 blocker
5. **看到好代码要夸** — 好的模式值得被看见、被学习

## 二、五大审查维度

### 2.1 正确性（Correctness）

代码是否做了它该做的事？

| 检查项 | 说明 |
|--------|------|
| 边界条件 | 空数组、null、undefined、超长字符串、并发请求 |
| 异步流程 | async/await 是否配对、Promise 是否有 catch、竞态条件 |
| 状态一致性 | 前端 store 与后端数据库是否可能不同步 |
| 错误处理 | 关键路径是否有 try-catch、错误是否被静默吞掉 |
| 类型安全 | 类型转换是否显式、`==` vs `===`（JS）|

**本项目典型案例：**
- `server.py` 第 72-78 行：CORS `allow_origins=["*"]` 配合 `allow_credentials=True`，在生产环境会导致浏览器拒绝请求（规范冲突），且存在安全风险
- `llmService.js` 第 133 行：`history.slice(-20)` 取最近 20 条，但注释说"取最近 10 轮"，实际逻辑与注释不一致

### 2.2 安全性（Security）

是否存在可被利用的漏洞？

| 检查项 | 说明 |
|--------|------|
| 注入风险 | SQL 注入、命令注入、XSS、Prompt 注入 |
| 认证授权 | Token 验证是否完整、是否有越权访问 |
| 敏感信息 | 密钥/密码是否硬编码、日志是否泄露敏感数据 |
| 输入校验 | 用户输入是否经过验证和清洗 |
| CORS/CSP | 跨域策略是否最小化 |

**本项目典型案例：**
- `auth.js` 第 3 行：`JWT_SECRET` 从环境变量读取 ✅ 正确做法
- 但第 14 行：`jwt.verify` 未指定 `algorithms` 参数，存在算法混淆攻击风险（攻击者可伪造 `alg: "none"` 的 token）
- `server.py`：推理服务绑定 `0.0.0.0` 且无任何认证，任何能访问网络的人都可调用

### 2.3 可维护性（Maintainability）

6 个月后接手的人能看懂吗？

| 检查项 | 说明 |
|--------|------|
| 命名 | 变量/函数名是否自解释、是否一致 |
| 函数长度 | 单函数超过 50 行考虑拆分 |
| 注释质量 | 解释"为什么"而非"做了什么" |
| 模块耦合 | 模块间是否通过明确接口通信 |
| 配置管理 | 魔法数字是否提取为常量/配置 |

**本项目典型案例：**
- `pipeline.py`：结构清晰，docstring 完整，argparse 有使用示例 ✅ 标杆代码
- `llmService.js`：`detectEmotion` 和 `detectCrisis` 的关键词列表硬编码在业务代码中，后续维护困难，建议提取到配置文件

### 2.4 性能（Performance）

有没有明显的瓶颈？

| 检查项 | 说明 |
|--------|------|
| N+1 查询 | 循环中是否有数据库/API 调用 |
| 内存泄漏 | 事件监听是否清理、大对象是否及时释放 |
| 不必要的计算 | 是否有重复计算可以缓存 |
| 并发控制 | GPU 推理是否有请求队列、是否会 OOM |
| 前端渲染 | 是否有不必要的重渲染、列表是否用 key |

**本项目典型案例：**
- `server.py`：推理服务是单线程同步处理，一个请求在生成时其他请求全部阻塞。在 DAU 5 万的目标下，这是严重瓶颈
- `authStore.js`：token 存在 localStorage 中，每次页面加载都会读取，虽然性能影响小但需注意 XSS 场景下的 token 泄露

### 2.5 测试（Testing）

关键路径有测试覆盖吗？

| 检查项 | 说明 |
|--------|------|
| 核心逻辑 | 情绪检测、危机识别、记忆检索是否有单元测试 |
| API 测试 | 主要接口是否有集成测试 |
| 边界测试 | 异常输入、超时、服务不可用是否覆盖 |
| 测试可运行 | 测试是否能独立运行、不依赖外部服务 |
| 回归保护 | 修 bug 时是否同步补充测试 |

**本项目现状：**
- `LLM/serving/` 有 `test_api.py`、`test_e2e.py`、`test_multiturn.py` ✅
- `Agent/server/` 无任何测试文件 🔴
- `Agent/client/` 无任何测试文件 🔴
- `LLM/data_pipeline/tests/` 有测试目录 ✅

## 三、分模块审查重点

### 3.1 Python ML 代码（LLM/）

```
重点关注：
├── 数据管道（data_pipeline/）
│   ├── 文件编码是否统一 utf-8
│   ├── 大数据集是否用流式处理（不要一次性 load 进内存）
│   ├── 增量处理逻辑是否正确（manifest 更新时机）
│   └── 配置文件是否有 schema 验证
├── 训练脚本（training/）
│   ├── 超参数是否可配置（不要硬编码）
│   ├── checkpoint 保存/恢复逻辑
│   ├── 随机种子是否固定（可复现性）
│   └── 显存管理（是否有 OOM 保护）
└── 推理服务（serving/）
    ├── 并发安全（全局模型 + 多线程）
    ├── 超时和取消机制
    ├── 输入长度限制（防止 OOM）
    └── 错误信息不泄露内部细节
```

### 3.2 Node.js 后端（Agent/server/）

```
重点关注：
├── 路由层
│   ├── 所有接口是否有 authMiddleware 保护
│   ├── 请求参数是否经过 validate 校验
│   └── 响应格式是否统一
├── 服务层
│   ├── 数据库操作是否用事务
│   ├── 外部 API 调用是否有超时和重试
│   └── 错误是否向上抛出而非静默处理
├── 中间件
│   ├── JWT 验证是否指定 algorithms
│   ├── 限流策略是否合理
│   └── 日志是否记录关键操作
└── 数据层（Prisma）
    ├── 查询是否只取需要的字段（select）
    ├── 关联查询是否有 N+1 问题
    └── 敏感字段是否有访问控制
```

### 3.3 React 前端（Agent/client/）

```
重点关注：
├── 组件
│   ├── 是否有不必要的重渲染（useMemo/useCallback）
│   ├── 事件监听是否在 useEffect 中清理
│   ├── 条件渲染是否处理了 loading/error/empty 三态
│   └── 列表渲染是否有稳定 key
├── 状态管理（Zustand）
│   ├── persist 的数据是否包含敏感信息
│   ├── 异步操作是否有竞态保护
│   └── 状态更新是否最小化（不要整个对象替换）
├── 网络请求
│   ├── 是否有统一的错误处理
│   ├── token 刷新逻辑是否处理并发
│   └── 请求取消（组件卸载时）
└── 样式
    ├── 是否遵循设计 Token 体系
    ├── 响应式断点是否使用统一变量
    └── 暗色模式是否适配
```

### 3.4 原生 Web 前端（web-app/）

```
重点关注：
├── app.js（IIFE 模块化）
│   ├── 模块间通信是否清晰
│   ├── 全局变量是否最小化
│   └── DOM 操作是否有 XSS 防护（innerHTML vs textContent）
├── CSS 模块化
│   ├── 是否使用 Token 变量而非硬编码颜色
│   ├── 选择器是否过度嵌套（不超过 3 层）
│   └── 媒体查询是否覆盖所有断点
└── 性能
    ├── 图片是否懒加载
    ├── 事件是否使用委托
    └── 动画是否用 transform/opacity（避免重排）
```

## 四、审查流程

### 4.1 流程总览

```
开发者提交 PR
    │
    ▼
自动化检查（CI）
├── Lint（ESLint / Ruff）
├── 类型检查（如有 TypeScript）
├── 单元测试
└── 安全扫描（依赖漏洞）
    │
    ▼ 通过
分配审查者
├── 1人必审（核心模块2人）
├── 48小时内完成审查
└── 审查者不能是代码作者
    │
    ▼
代码审查
├── 第一轮：完整审查（所有维度）
├── 作者修复 → 回复每条评论
├── 第二轮：确认修复 + 回归检查
└── 特殊情况：面对面/语音讨论
    │
    ▼
合并
├── 所有 🔴 问题已解决
├── 🟡 问题有明确跟进计划
├── CI 全绿
└── Squash merge（保持历史整洁）
```

### 4.2 PR 提交规范

```markdown
## PR 模板

### 变更说明
<!-- 一句话描述做了什么 -->

### 变更类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 性能优化
- [ ] 配置变更

### 影响范围
<!-- 哪些模块/接口受影响 -->

### 测试情况
- [ ] 新增/修改了单元测试
- [ ] 手动测试通过

### 自检清单
- [ ] 代码通过本地 lint

- [ ] 关键路径有错误处理
```

### 4.3 审查者分配规则

| 模块 | 主要审查者 | 备选审查者 | 说明 |
|------|-----------|-----------|------|
| LLM/training/ | ML 工程师 | 后端工程师 | 训练脚本变更影响大，需双人审 |
| LLM/serving/ | ML 工程师 + 后端 | - | 涉及并发和 API 设计，必须双人 |
| Agent/server/ | 后端工程师 | 全栈 | API 变更需检查前后端一致性 |
| Agent/client/ | 前端工程师 | 全栈 | UI 变更需附截图 |
| web-app/ | 前端工程师 | - | 相对独立，单人审即可 |
| 配置文件/CI | 任意工程师 | - | 低风险，快速通过 |

### 4.4 审查时间承诺

| PR 规模 | 审查时限 | 说明 |
|---------|---------|------|
| < 50 行 | 24 小时 | 小修复，快速响应 |
| 50-200 行 | 48 小时 | 常规功能开发 |
| 200-500 行 | 72 小时 | 大功能，建议拆分 |
| > 500 行 | 拒绝审查 | 要求拆分后重新提交 |

## 五、审查评论规范

### 5.1 优先级标记

| 标记 | 含义 | 合并条件 |
|------|------|---------|
| 🔴 | Blocker - 必须修复 | 不修不能合并 |
| 🟡 | Suggestion - 建议修复 | 可本次或下次迭代修 |
| 💭 | Nit - 小瑕疵 | 不阻塞合并 |
| 👍 | Praise - 写得好 | 纯表扬 |
| ❓ | Question - 有疑问 | 需要作者解释 |

### 5.2 评论格式模板

```markdown
🔴 **安全: JWT 算法混淆攻击**
文件: `server/src/middleware/auth.js` 第 14 行

**问题:** `jwt.verify(token, JWT_SECRET)` 未指定 algorithms 参数。

**为什么:** 攻击者可构造 header 为 `{"alg": "none"}` 的 token 绕过验证，
或使用 RS256 公钥作为 HS256 密钥伪造签名。

**建议:**
```js
const decoded = jwt.verify(token, JWT_SECRET, { algorithms: ['HS256'] })
```

**参考:** https://auth0.com/blog/critical-vulnerabilities-in-json-web-token-libraries/
```

### 5.3 禁止的评论方式

❌ "这代码写得不好"（不具体）
❌ "你怎么又犯这个错误"（对人不对事）
❌ "改了"（无解释）
❌ 只说问题不给方案
❌ 在公开 PR 中讨论绩效/能力

## 八、审查文化建设

### 8.1 审查者守则

1. **先理解意图，再看实现** — 读 PR 描述，不清楚就问
2. **区分偏好和标准** — "我更喜欢这样写"不是审查意见
3. **给出具体建议** — 不要只说"这里不好"，要说"建议改成 X 因为 Y"
4. **及时响应** — 不要让 PR 等超过承诺时间
5. **承认不确定性** — "我不确定，但..."比假装全知好

### 8.2 作者守则

1. **PR 要小** — 一个 PR 解决一个问题，200 行以内最佳
2. **自己先审一遍** — 提交前自己 diff 一遍，消灭低级错误
3. **回复每条评论** — 即使不同意，也说明原因
4. **不要玻璃心** — 审查的是代码，不是你
5. **学到东西要记录** — 好的审查意见沉淀为团队规范

### 8.3 定期回顾

- **每两周**：统计审查数据（PR 数量、平均审查时长、blocker 比例）
- **每月**：回顾高频问题，更新检查清单
- **每季度**：审查标准大版本更新，纳入新发现的模式
