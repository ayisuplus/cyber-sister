# 人设深度化：书面计划（第一阶段）

> 状态：📝 草案待审。产品负责人批准前不开工；批准后按下面的任务逐个做。
> 日期：2026-10-06。依据：产品负责人当日四项裁定（见 §1）、路线图 C30、对 `alchaincyf/nuwa-skill`（下称 nuwa）的阅读与对本仓库的核对。

## 0. 为什么要做

人设库（C30）最初是想借 nuwa 的做法：把「一个人怎么想、怎么说」蒸馏进「她」。实际做出来的是一张七格表加一次模型调用，没有借到 nuwa 的方法。核对结果（代码为证）：

| nuwa 的做法 | 本仓库现状 |
|---|---|
| 六路并行调研，区分一手 / 二手来源 | 一个调研回合，系统提示就是「整理成 JSON 卡」那段，**没有告诉它查什么**；调研笔记用完即丢，无出处 |
| 3–7 个心智模型，带证据与失效条件；5–10 条「如果 X 就 Y」 | 「她怎么看事情」400 字文本框、「她遇事怎么判断」300 字文本框 |
| 表达风格五个维度 | 「她怎么说话」400 字 + 至多 5 句示例 |
| 诚实边界（≥3）与内在矛盾（≥2）必填 | **没有这两项** |
| 造完做三项测试（已知立场 / 未公开问题 / 声音） | 只校验字数和两条启发式；之后全靠用户自己改 |
| 成品 400–600 行 | 整张卡所有字段加起来最多约 2300 字，蒸馏输出上限 1500 token |

另外两个独立的问题（不属于 nuwa 的范畴，一并处理）：
- 「男性」那道闸太粗：`MALE_MARKS` 里的「男人」「男性」会误伤正常写法。已用同一条正则实测，「她很会分析男人的心思」「不喜欢男人，只爱吃甜点的都市女孩」「她是个女生，对男性话题很敏感」都被拒。
- 沉浸「中」档：界面写「聊到要紧事也能出来直说」，身份线提示词里没有这句。

## 1. 已裁定的输入（2026-10-06，产品负责人）

1. **想借 nuwa 的是**：造「像某个人」的她；把「她怎么想」做深；让用户把自己的朋友「留下来」。
2. **朋友这条路**：只限**在世**的朋友，**文字素材**；不收照片、不联网查人、原始聊天记录不保存、用户勾选声明、她不能自称是那个真人；已故亲友不做。
3. **「像某个人」的范围**：虚构角色 + 公开资料充足的**女性**公众人物；公众人物卡标明「受公开言论启发的 AI，不代表本人」，不编造语录；男性一律拒绝（沿用 C30 硬规则）。
4. **先做什么**：先做**结构**，不动调研流水线。
5. **诚实与验证**：作为卡的数据结构里的**硬要求**（标来源或推断、边界与矛盾必填、造完自检）。

## 2. 第一阶段做什么、不做什么

**做**：卡的深度结构（v2）、每轮注入的精简核心、三种来源类型及其规矩、蒸馏提示词与输出结构、修两个已确认的问题、表单、评测装置的离线扩展、文档。

**不做**（留给后续阶段，各自要另行批准）：
- 多路并行调研与带 URL 的来源追溯（第二阶段）；
- 造完的「留出一部分」盲评自检（第三阶段，要真实调用模型，花钱，每次先问）；
- 已故亲友；朋友路径的照片；按每轮话题检索判断规则；删除内置 `PERSONA_BODIES`（评测与迁移仍在用）。

## 3. 卡 v2 的结构

在现有七格上**只加可选字段**，旧卡（以及手写的卡）原样有效，不需要数据库迁移（`Persona.card` 本身是 JSON）。

```
provenance: { kind: original | fiction | public_figure | friend,
              label: ≤30 字（原作名 / 人物名；friend 可为空） }
expression: { sentence, vocabulary, rhythm, humor, certainty }   各 ≤80 字
heuristics: [{ when ≤60, then ≤100, basis: source | inferred }]   ≤8 条
models:     [{ name ≤20, idea ≤100, failsWhen ≤80, basis }]       ≤4 条
values:     [≤40 字]                                              ≤3 条
tensions:   [≤120 字]                                             ≤4 条
boundaries: [≤80 字]                                              ≤6 条
```

**诚实硬要求的口径**（我的解读，待你确认，见 §7 D2）：
- 凡 `kind` 不是 `original`（即蒸馏出来的卡）：`heuristics` ≥3 且每条都有 `basis`，`tensions` ≥2，`boundaries` ≥3，否则保存与蒸馏都拒绝；
- 手写的 `original` 卡不强制，用户想写多简单都行（C30「不设风格门槛」不变）。

## 4. 运行时注入

- v1 的七行拼装**逐字不变**（有测试保证旧卡输出与现在字节一致）。
- v2 只在其后**追加**一段，最多 600 字，按优先级整条取舍（不截半句）：判断规则（前 5 条）→ 表达（口头禅与节奏）→ 价值观与矛盾 → 一句边界（「你不知道的、做不到的就直说」）。
- `public_figure`：另加一行——你是受 {label} 公开言论启发的 AI，不代表本人；不编造她说过的话；不自称是她。`friend` 同理不得自称是那个真人。
- 提示词顺序不变：安全边界 > 身份线 > 共用前言 > 人设层。身份线与危机检测不受影响。

## 5. 三条来源路径的规矩

| | 虚构角色 | 公众人物 | 朋友 |
|---|---|---|---|
| 素材 | 用户文字 + 照片（可选） | 同左 | **只用文字**，照片一律 400 |
| 联网调研 | 沿用现状（`SEARCH_ENABLED` 才开） | 同左 | **服务端强制关闭**，用户传 `research=true` 也无效 |
| 声明 | — | — | 必须 `attested: true`（我有权使用这些聊天记录，对方是在世的朋友） |
| 标注 | 卡上显示「虚构角色」 | 「受公开言论启发的 AI，不代表本人」 | 「来自你提供的聊天记录」 |
| 原始素材 | 不落库（现状） | 不落库 | 不落库，处理完即丢 |

朋友路径放在服务端开关 `PERSONA_FRIEND_ENABLED` 后面，**默认关闭**，直到法务确认（见 §7 D3）。

**T2 的男性闸验收表**（在测试里写成表）：
- 必须拒绝：「我是男生」「我是个男生」「人设是男的」「男闺蜜」（启发式只拦这类明说，拦不全，界面照旧如实说明）；

## 7. 需要你确认的点

- **D1 沉浸「中」档**：界面承诺「聊到要紧事也能出来直说」。我推荐把它**写进提示词**（遇到情绪危机、健康、重大决定先从角色里出来认真说），而不是删界面文案——这是更安全的方向，且不弱化「不冒充真人」。
- **D2 诚实硬要求只管蒸馏出来的卡**，手写卡不强制。
- **D3 朋友路径默认关闭**（服务端开关），法务确认后再开。
- **D4 抽共享包**（T1）。不抽也能做，但卡字段翻倍后，两处各抄一份的漂移风险也翻倍。

## 8. 验证与评审

- 每项先跑最窄的测试，再跑：`pnpm typecheck`、`pnpm lint`（API 上限 146 已经顶满，新增代码**不得**增加告警）、API / Web / 网关 / 共享包单测、Playwright 桌面与手机。
- T6 完成后做一次**独立评审**（`code-review`），再请你验收。
- 没有任何真实模型调用、没有部署；每次要真实调用（含第三阶段自检）都先问你。

## 9. 风险与限制

- 朋友路径涉及第三方个人信息交给云端模型；隐私政策目前仍是草案，真要对外发行必须由法务确认，这里只做技术保护。
- 「男性」闸改窄后，启发式依然拦不全，界面照旧如实说明。
- nuwa 的数字（3–7 个模型、5–10 条规则、≥3 条边界等）来自对它 README 与 SKILL.md 的阅读，这里取其结构、不取其规模。
- 我没有跑过任何真实的蒸馏或调研；第一阶段的「更好」靠结构与测试保证，不靠模型效果实测。
