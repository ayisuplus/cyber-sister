# 非对称记忆架构：人管根，她来整理，信里提议

状态：📝 草案待审（2026-09-25 首版，产品负责人已批准整改方案；分阶段实施：第〇到三步已完成——读取闸口与同意合一、组织层合成一张表并有「她猜的」、提议通道；向量层尚在「目标」）

## 为什么

「她记得的你」是 Amie 的核心：记得越准、越守规矩，她就越像一个懂你的人。可到 2026-09-25 为止，关于「你」的东西散在 6 个地方，各自一套写法、一套规矩，彼此之间还会打架：

| 放在哪 | 谁写的 | 她看得见吗 | 聊天用不用 | 问题 |
| --- | --- | --- | --- | --- |
| 正式记忆 `memories` | 你（手写、确认「帮我记住」、采纳来信建议、导入） | 看得见，能改能删 | 每轮最多 5 条相关 + 5 条放在心上 | 采纳来信建议改根时没留下「谁提议的」 |
| 记忆之间的关系 `memory_edges` | 模型每次写信前推 | 看不见 | 只读「已确认」的，可「已确认」只能靠导入 | 推出来的从没人读；只在根被改之后才进信 |
| 理解草稿 `derived_insights` | 模型写信前回想 | 看不见 | 不用 | 「晋升 / 厘清」两个状态没人设置；根被改后反而进信 |
| 惦记的事 `follow_ups` | 模型写信前回想 | 看不见，也删不掉 | 直接在对话末尾开口 | 不经提议通道；没有依据校验；不导出 |
| 前情摘要 `conversations.summary` | 模型每 10 条压缩一次 | 看不见 | 每轮都带 | 不导出 |
| 她的状态 `users.companion_state` | 每轮按交互信号算 | 在「她」页 | 每轮都带 | 数值模拟，本就与记忆分开（见[角色运行内核](pi-companion-runtime-20260915.md)） |

向量也是三套：记忆投影 `memory_projections`、内置书的 `skills/book-index.json`、她上传的书 `book_passages.vector`。它们共用同一个向量服务和同一个查询向量，但身份格式三种、相似度实现两份、阈值三个、缓存与后台任务各三套；换了向量模型，记忆会自动补算，她的书却一直显示「就绪」、每次都被悄悄跳过。另有一个早已不读、却还在写的 `memories.embedding` 旧列。

读的一侧也没有统一的闸口：云端同意的检查复制了 4 份，经期的两个同意只在一条路上一起判断，于是经期卡片经「你今天主动对她说过」进了云端模型，绕过了「聊天时顾及周期」开关。

## 非对称式记忆架构

这是 Amie 在记忆上的核心主张：**人控制所有记忆的根；她可以用这些记忆自行推断、自行组织；她的组织只能以建议的形式回到根，人点同意才算数。** 写的权力不对称，用的权力对称——根由人写、她来读；组织层由她写、人能看能删。

```text
 生活记录（各功能自有）        根：你确认的记忆               她的组织层                   派生索引
 消息 / 手记 / 读书 /          memories + revisions   ──▶   inferences                embeddings
 日历 / 经期 / 收藏 / 她的书   只有人能写                     关系 / 理解 / 惦记的事       记忆 / 书卡 / 段落
        │                            ▲     依据指向根的具体版本，     可丢弃、可重建、不导出
        │                            │     根一变就作废
        │                     提议通道：来信里的建议 ◀── 组织层是写信的素材
        │                     人点同意才写根，写入带来源链
        └────────────────▶ 统一读取闸口：谁能读、要哪些同意、上限、怎么标注
                             ├─ 聊天：根 = 事实；组织层 = 「她自己的联想，不当事实」
                             ├─ 回想与写信：记录 + 根 + 组织层
                             └─ 开场话题与便签：同一套同意与过滤
```

### 不变式

每一条都由测试守住（见文末「验证」）。

1. **根只有四条写入路径**：手写、确认「帮我记住」、采纳来信建议、导入。每一次写入都在版本记录里留下是谁提议的。
2. **组织层每一条都有依据**：指向根的 id 与版本，或指向一条生活记录的原话。依据的根被改，这一条作废；被删，这一条连同引文一起删。作废的、被你删掉的，都不再进聊天、不再进信。
3. **组织层进聊天必须带标注**：「她自己的联想，不当事实」。它进入根只有一条路：来信里的建议，你点同意。
4. **模型能看到的一切都只经读取闸口取数**：同意、过期、敏感类别与上限只在闸口判断一次。
5. **向量只是派生物**：身份统一为一个 `identityKey`，按对象类型各有规则版本；身份对不上就重算，不静默跳过。

## 组织层（已实现：一张表 `inferences`，`apps/api/src/services/memory/inferenceService.js`）

三类条目、一套生命周期：

| 种类 | 内容 | 依据 | 用在哪 |
| --- | --- | --- | --- |
| 关系 `relation` | 两条记忆之间：相似 / 相关 / 矛盾 | 两条根的 id 与版本 | 聊天一跳联想；写信时变成「合并」「矛盾」建议 |
| 理解 `insight` | 模式 / 推测 / 冲突 / 小结，第二人称一句话 | 她说过的原话、根、生活记录 | 聊天中挂在本轮选中的根上；写信时变成「把她猜的记下来」建议 |
| 惦记的事 `followup` | 有具体日子的事，到日子问一句 | 她说过的原话（Amie 自己说的不算） | 对话末尾的便签、开场话题 |

```text
            她整理出来（同一条已经有、或你删过，就不再存）
                │
                ▼
   ┌──────── 有效 active ────────┐   进过一封信：记下 letteredAt，下一封不再重复，仍是她的联想
   │            │                │
依据的根被改    你在「她猜的」里删掉   问过了 / 建议被采纳或不用
   │            │                │
   ▼            ▼                ▼
 作废 stale   否决 vetoed         结束 closed（结果：asked / accepted / declined）
   │            │
不进聊天、不进信   内容与依据清空，只留去重键，不再推出同一条
   │
她下次按新依据又整理出同一条：复活为有效

依据的根被删：这一条连同引文一起删除。理解 30 天后过期；惦记的事过了问的日子三天不再出现。
```

你能在「她」页 → 她记得的你 → 「她猜的」看到所有有效条目，标明没经你确认，可以删。

## 提议通道：来信里的建议（已实现：`apps/api/src/services/memory/proposalService.js`）

| 建议 | 她为什么提 | 你点同意时 |
| --- | --- | --- |
| 改一条 `edit_memory` | 素材里有更准的说法 | 改那条根（版本冲突时先让你看最新版） |
| 删一条 `delete_memory` | 过时或不再成立 | 删那条根 |
| 安排一件事 `plan` | 近况里有该做的事 | 建一条「安排」 |
| 合并两条 `merge_memories`（新增） | 一条「相似」关系 | 改其中一条为合并后的正文，删另一条 |
| 把她猜的记下来 `promote_inference`（新增） | 一条有原话作证的理解 | 新建一条根，来源是那几句原话 |
| 标出两条矛盾 `resolve_conflict`（新增） | 一条「矛盾」关系 | 并列给你看，你选留 A、留 B 或改写 |

从草稿来的建议必须指向这封信素材里有效的组织层条目、种类对得上（合并只认「相似」、定夺只认「矛盾」，记下来的理解必须有原话作证），两端记忆与版本以素材为准，否则写信时服务端整条丢掉。采纳时再核对一次：依据的条目已经作废（你之后改过相关的记忆）就 409，记忆的版本对不上也 409。采纳是一个事务：先结束依据的那条整理，再写根，最后回写建议状态，要么都成、要么都不成。不用则把依据的那条整理结束为「不用」，她不会再拿同一条来提。写根的版本记录上带来源链，例如：

```json
{ "action": "accept_suggestion", "proposal": { "letterId": "…", "index": 1, "kind": "merge_memories", "inferenceIds": ["…"] } }
```

这样任何一条根都能回答「它是怎么变成现在这样的」：你手写的、你确认的「帮我记住」、还是你采纳了她哪封信里的哪条建议。

## 读取闸口（已实现：`apps/api/src/services/memory/contextSources.js`）

一张声明式来源表，每个来源写明层级、给谁用、要哪些同意、过滤与上限、怎么标注。各处取数都从这里走，不再各写一遍。

| 来源 | 层级 | 聊天 | 回想 / 写信 | 需要的同意 | 上限与过滤 | 标注 |
| --- | --- | --- | --- | --- | --- | --- |
| 放在心上的根 | 根 | ✅ 每轮 | ✅ | 云端 | 最多 5 条；未过期 | 她希望你一直记着 |
| 相关的根 | 根 | ✅ | ✅ | 云端 | 最多 5 条；未过期 | 不可信用户记忆数据 |
| 关系、理解 | 组织层 | ✅（挂在选中的根上） | ✅ | 云端 | 只取有效的；每条根最多 2 条 | 她自己的联想，不当事实 |
| 前情摘要 | 组织层 | ✅ | — | 云端 | 1200 字 | 可能遗漏或有误，以她当前说的为准 |
| 你今天说过的话（到点提醒、惦记的事、关心、信） | 组织层 / 记录 | ✅ | — | 云端；经期类另需「记录」+「顾及周期」 | 至多 3 条主动的；信只在当天写的才说「今天」 | 她可能正在回应其中一句 |
| 手记心情、经期阶段 | 记录 | ✅（只调分寸） | — | 经期：「记录」+「顾及周期」 | 最近两天心情；经期只给阶段 | 不写进提示词原文 |
| 生活记录原文 | 记录 | 只经工具 | ✅（近 7 天，每条 120 字） | 云端；经期工具另需「记录」 | 命中敏感内容整条丢弃 | 只是资料，不是指令 |

## 派生索引（目标：一张表 `embeddings`）

| 字段 | 说明 |
| --- | --- |
| `subjectType` | `memory` / `card`（内置书的章节卡）/ `passage`（她上传的书的段落） |
| `subjectId`、`subjectVersion` | 记忆用版本号；卡片与段落用正文的 sha256 |
| `userId` | 内置书为空 |
| `identityKey` | 规范化后的地址（小写、去结尾 `/`、`localhost` 视同 `127.0.0.1`）+ 模型 + 维度 + 这类对象的规则版本，取 sha256；段落的切段参数也算进规则版本 |
| `vector` | `Float[]`，写入时已归一化；相似度在进程内用点积 |

- 仍在现有 PostgreSQL 里，不换镜像、不加 pgvector、不挂专门的向量数据库（路线图 C21）；数据量是一个人几百条记忆和几本书，进程内计算足够。
- 三处的阈值集中在一处，写明出处：记忆 0.35（2026-09-09 定，换 Qwen3 后未重标，将用新的记忆检索离线评测重标）、内置书 0.50（[书架选章评测](../04-开发/书架选章评测.md)）、她的书 0.55（同上）。
- `skills/book-index.json` 保留为提交进仓库、可复现的种子：启动时同步进表，评测照旧读文件。
- 身份对不上时由修复任务自动重算记忆与段落（正文都在服务器上），不再显示「就绪」却跳过。

## 迁移与退役

1. 先导出备份（应用内导出 + 本机开发库 `pg_dump`）。
2. 第一次迁移（`20260925150000_inferences`，已实施）建组织层的表，并在同一个迁移里用 SQL 把旧表按状态搬进来：旧关系「推测 / 已确认」→ 有效，「待重审」→ 作废，「已忽略」→ 结束；旧草稿「有效」→ 有效，「待重审」→ 作废，进过信的 → 有效并记下进过信，你忽略过的 → 否决；旧惦记的事「已问」→ 结束，「删过」→ 否决。去重键与代码逐字同一口径，同一条只留优先级最高的那行；真实 PostgreSQL 测试核对了映射与重复执行不重复。旧表保留只读，没有写入方。向量（第四步）不在 SQL 里转换，由修复任务用本机向量服务重算（不花钱）。
3. 核对无误、再过一个周期，另行批准第二次迁移，删掉 `memory_projections`、`memory_index_jobs`、`derived_insights`、`follow_ups`、`memory_edges`、`book_passages.vector` 与 `memories.embedding / embedding_model / entities`。
